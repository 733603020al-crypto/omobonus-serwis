# Ветки, коммиты, безопасность

## Git: commit, push, ветки

Commit, push и merge — только после явного разрешения пользователя на соответствующее действие. Перед разрешёнными Git-изменениями: ветка соответствует задаче (см. «Ветки»); для `master` пользователь отдельно назвал конкретное действие; `git status --short` содержит только ожидаемые файлы задачи; нет изменений `.env*`; цены/контакты/форма/юридический текст менялись только по прямому заданию; если менялся код сайта — `npx tsc --noEmit` прошёл и сборка прошла (в копии, см. `.claude/skills/optimization-check/SKILL.md` §5); для правок только инструкций и документов сборка не нужна. Commit message — короткий, по смыслу. Push выполняй только в явно названную пользователем ветку, каждый раз по отдельному разрешению.

Сообщение коммита — по-русски и содержательно: что именно сделано или исправлено, чтобы по одному сообщению было понятно изменение (не одна короткая английская строка). Если пользователь продиктовал английский текст — всё равно писать по-русски.

`git add -A` — только после проверки `git status --short`, что там только ожидаемые файлы; иначе точечный `git add <path>`.

**Ветки:**
* `test` — правки, оптимизация и проверки существующего сайта.
* Новая страница — в отдельной ветке `pages/<название-страницы>` (можно в отдельной рабочей копии со своим портом). Создание ветки и включение страницы в `test`, меню или на главную — только по согласованию с пользователем.
* Любая другая ветка — только если пользователь явно назвал её для этой задачи.
* `master` — защищена, см. «Безопасность».

Перед изменениями молча проверь текущую ветку. Если она соответствует задаче по правилам выше — продолжай автономно, не спрашивай про ветку каждый раз. Если не соответствует — останови работу и ничего не меняй, спроси пользователя (не переключай ветку самостоятельно).

**Основная папка всегда на `test`.** Никогда не переключать её на `master` (даже после слияния). В начале сессии, если ветка `master` — самому выполнить `git switch test` (несохранённые правки сохраняются) и одной фразой сообщить пользователю; до переключения ничего не менять.

Если пользователь написал «не commit», «не push», «только аудит», «ничего не менять», «read-only» — обязательно соблюдай это ограничение.

**Пуши — только пачкой.** Каждый пуш создаёт Preview в Vercel и копит место. Выполнив задание, не делать и не предлагать commit/push; в отчёте одной строкой «не сохранено в гитхаб». Только когда пользователь скажет «сохрани» — собрать накопленное в один пуш. Другим сессиям commit/push не поручать.

## Безопасность

* Не читай `.env`, `.env.local`, `.env.production`, `.env.development`, ключи, токены, пароли, секреты без разрешения — даже в audit-режиме. Не выводи секреты в ответ.
* Не устанавливай новые пакеты без подтверждения. Исключение: `npm install` для восстановления библиотек по package-lock (без новых пакетов и без изменения package.json) — разрешён постоянно.
* Не запускай опасные команды: удаление файлов, очистка базы, `git reset/rebase/clean`, деплой и отправка секретов наружу.
* Ветка `master` защищена. Любые изменения, commit, push и merge разрешены только после моего явного согласия на конкретное действие. Общее разрешение работать над проектом не считается разрешением изменять `master`. Работай в ветке, подходящей для задачи (см. «Ветки»).

## Рабочие копии и порядок публикации

**Человеческим языком.** У сайта несколько отдельных рабочих папок (копий): основная, «тест» и по одной на каждую новую страницу. В каждой папке — своя работа, и в одной папке одновременно работает только один помощник, иначе правки перемешиваются. Страница идёт так: своя копия → «тест» (по вашему «да») → «мастер» (отправляете вы сами).

Правила:
* Одна сессия — одна папка: прежде чем править, `git status --short`; чужие несохранённые изменения не трогать и не стейджить (точечный `git add <файлы>`).
* Защита мастера: в `.git/hooks` стоит `pre-push`: при пуше в `master` один раз просит пользователя нажать Enter в терминале (Ctrl+C — отмена) с предупреждением про боевой сайт. Без терминала (сессии Клода) пуш в `master` блокируется. Строка для пользователя — обычный `git push origin master`, без переменных.
* Порядок: страница → `pages/<slug>` → `test` (по разрешению) → `master` (отправляет пользователь). Подробнее — `docs/standards/new-page-standard.md`.
* Публикация в `test` — только быстрым пушем, без перезаписи: `git fetch`, `git merge-base --is-ancestor origin/test HEAD`, затем `git push origin HEAD:test`. Если проверка не прошла — сначала влить `origin/test` в свою ветку, не форсировать.
* В `master` отправляет пользователь: защита блокирует merge/push. Дать одну готовую строку для терминала, затем проверить боевой сайт.
* Сборка (`npm run build`) — только в отдельной копии: в основной папке она ломает работающий dev-сервер.
