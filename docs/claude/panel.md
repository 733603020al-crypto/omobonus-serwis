# Панель Omobonus Workspace: оформление, разработка, отложенные задачи

## Главные требования
- **Chrome и визуальные проверки запрещены.** Браузер, скриншоты, визуальные и попиксельные проверки Workspace — только по отдельному разрешению пользователя на конкретный случай; единственное исключение — автопроверка `npm run check:ui` (раздел «Автопроверка интерфейса» ниже). По умолчанию проверять кодом: типы (`npx tsc -p tsconfig.app.json --noEmit`), `npm run check:design`, `npm run test:design`, `npm run test:tree`. Повторные диагностики не запускать. Это правило главнее общего требования об итоговой визуальной проверке.
- **Меньше информации.** На экране только нужное: лишние подписи, блоки, подсказки и «историю ради истории» убираем. Больше места под данные.
- **Минимум текста над содержимым (стандарт интерфейса).** Под заголовком страницы нет вводных строк, пояснений и информационных полос: описание — в подсказке у значка «i» рядом с названием (поле `description` у `PageHeader`), счётчики — компактными значками в углу. Всё освободившееся место — основному содержимому. Предупреждения, ошибки, обязательные сведения и нужная помощь остаются. Действует для всех существующих и новых страниц.
- **Для человека, а не для машины.** Названия, тексты и правила — по-русски, простыми словами, без техжаргона. Техническое прячем в свёрнутый блок «Для Claude (техническое)».
- **Структура видна глазами.** Схема или таблица вместо длинного текста; всё собрано в одной панели и разложено по разделам.
- **Один раздел — одна тема.** Не смешиваем (языки не кладём в SEO).
- **У каждого раздела — кнопка «Правила»** с понятными правилами этого раздела.
- **Минимализм и единый стиль.** Современное, лёгкое оформление: без крупных заголовков и больших букв; пункт меню, на котором стоим, выделен заметно (цвет и фон). Основной экран строим как левое меню: категории, которые по умолчанию свёрнуты — выбираешь и открываешь нужную. Внутри файла правил тоже есть меню-выбор разделов. Всё в одном стиле.

## Единый стандарт документов (обязателен для всех существующих и будущих)
- Любой документ, правило или инструкция Workspace открывается только в существующем просмотрщике (страница `/seo/rules/<id>`, компонент в `app/src/pages/seo-rules.tsx`): слева кликабельное оглавление разделов, справа содержимое, сверху «Редактировать» (если документ редактируемый). Эталон — «Запуск новой страницы».
- Структура: категория → подкатегории любой вложенности → документ → разделы. Дерево — в левом меню (`app/src/lib/rules-groups.ts`); у раздела с документами есть стрелка раскрытия, клик по названию тоже раскрывает и закрывает.
- **Без числовых префиксов.** В названиях категорий, подкатегорий, документов, разделов и пунктов меню номера («1. Клиенты», «### 2. Правила») не пишем; порядок задаётся порядком в дереве. Просмотрщик сам скрывает номера в начале заголовков (в тексте и оглавлении), файлы при этом не меняются.
- **Любое дерево (меню, оглавление категорий) — по WAI-ARIA Tree View и только через единый компонент `TreeView`** (`app/src/components/tree-view.tsx`, логика — `app/src/lib/tree-model.ts`). Свои раскрывашки и `Collapsible` для деревьев не делать; роль `treeitem` выставляет только этот компонент. Вид задаёт «оболочка» (skin), поведение одно:
  - выбранный пункт один на всё дерево и вычисляется только из адреса страницы (`?section=…` для базы знаний); сворачивание веток выбор не меняет, свёрнутый предок выбранного подсвечен; выбранный пункт всегда подсвечен и открывает справа свой документ;
  - **поведение веток одно для всех деревьев (аккордеон на каждом уровне):** повторный щелчок по ветке или стрелке сворачивает её; открытие другой ветки закрывает соседние (вместе с их вложенными); клавиша `*` не действует; при первом запуске открыт один раздел;
  - раскрытость хранится отдельно (localStorage), переживает обновление страницы и переходы; при смене выбора путь к нему раскрывается сам;
  - разметка: `role=tree/group/treeitem`, `aria-level/setsize/posinset/selected/expanded/current`, один пункт в Tab (roving tabindex); клавиши ↑ ↓ Home End → ← Пробел `*` и буква;
  - у каждого пункта уникальный id и уникальный адрес (иначе выбор неоднозначен).
- **Тесты обязательны:** при любом изменении деревьев запускать `npm run test:tree` в `omobonus-workspace/app` (`tests/tree-nav.test.mjs`, браузер не нужен); новый тип пункта или клавишу — добавлять в тесты.
- Новый документ: файл + запись в дереве + id в серверном списке файлов (`workspace-api.ts`). Отдельные редакторы, вкладки «Правила» внутри страниц и свои просмотрщики не создавать. Публикации Google — id `gp-*`, база знаний — `kb2-*` (только чтение).

## Единый шаблон оформления правил (обязателен для всех разделов Workspace)
Любое правило в Workspace оформляется карточкой с такими строками, в таком порядке:
- **Правило** — что делать.
- **Условие** — когда применять.
- **Варианты** — способы выполнения.
- **Примеры** — готовые образцы.
- **Исключения** — когда не применять.

Пустые строки не показываются; если пусты все — одна надпись «Пока не заполнено». Содержимое действующих правил при переносе в шаблон не меняется. Остальные разделы переводятся на шаблон по мере правок.

Три типа записей (пример — «Коммуникации → Ответы на письма»): **Правило** (правило, условие, варианты, примеры, исключения), **Инструкция** (действия, условия, результат, ошибки), **Шаблон ответа** (готовый текст, условия применения, переменные). У каждой записи: статус (черновик / на согласовании / утверждено), приоритет (высокий / обычный / низкий), связи с другими записями (взаимные), заметка, история изменений с прежним текстом, поиск по всем записям. Статусы: «Утверждено» — только если запись создана или изменена по прямому указанию владельца (в том числе правкой в панели) либо он явно её утвердил; заполненность полей утверждением не считается. Предложенное Claude самостоятельно — «На согласовании». «Черновик» — незавершённая запись. Источник решения хранится в поле записи (владелец / Claude); вручную выбранный статус не перезаписывается. Повторяющийся текст не дублируется, а заменяется ссылкой на основное правило (прежний текст остаётся в истории); готовые примеры писем не сокращаются. Удаления записей нет. Данные — в `omobonus-workspace/service/kommunikacii/client-replies-items.json`; исходный стандарт (`.claude/skills/odpowiedzi-klientom/SKILL.md`) не менялся. Код — `app/src/pages/client-replies.tsx`, `app/src/components/reply-item.tsx`, `app/src/lib/replies-model.ts`; проверка целостности — `npm run test:replies`.

## Автопроверка интерфейса (check:ui)
- **Правило:** после каждого значимого изменения интерфейса Workspace запускать `npm run check:ui` в `omobonus-workspace/app` (Playwright; проверяет поведение, размеры, состояния и вид). Работа не считается завершённой, пока проверка не пройдена; при провале исправить причину и повторить. Оригинал — эталон; расхождения не скрывать, эталоны сами не обновлять (создаются только флагом `--create-baseline` по решению владельца).
- **Условия:** только локальный сервер `127.0.0.1:5180`, подменённые тестовые данные, чистый Chrome без профилей владельца, внешние адреса заблокированы. Сейчас покрыто: главное левое меню и меню окна карточки `/processes` на 1440 и 390 px.
- **Лимит снимков (обязателен для всех задач Workspace):** максимум 2 скриншота на всю задачу — один эталонный и один итоговый; лимит общий, не на экран, состояние, запуск или попытку. Поведение, DOM, размеры и ошибки Playwright проверяет многократно без снимков. Изображения сравнивать только программно; снимки и большие логи в контекст не загружать. Серии снимков, повторные визуальные эксперименты и бесконечные циклы проверок запрещены. Не хватило двух снимков — остановиться и спросить разрешение владельца. Счётчик: `check:ui` ведёт его сам, новая задача — флаг `--new-task`.
- **Отчёт:** коротко — что отличается, насколько и где; полные результаты лежат в файле `ws-check-ui-results.json` во временной папке.

## Разработка панели (Omobonus Workspace)

Для календаря заданий единый договор и команда регрессионной проверки находятся в `C:/Users/Andrii/omobonus-workspace/app/docs/calendar-spec.md`; перед доработками календаря читать этот документ, перед завершением запускать описанный в нём полный набор тестов. Требования здесь не дублировать.

Для всех этапов разработки Workspace (код — `omobonus-workspace/app`, облачная панель — `omobonus-panel`) действует этот подход; он важнее общих правил о согласованиях выше. Цель — быстро получать готовые работающие функции. Приоритет: готовые функции, минимальная сложность, сохранность данных.

1. Получив задачу, сам выполняй весь согласованный этап: исследование, реализацию, тестирование, исправление ошибок.
2. Не спрашивай разрешения на мелочи. Безопасные изменения кода и commit + push в рабочие ветки (не `main`/`master`) разрешены.
3. Незначительные замечания, которые не мешают работе, — в журнал задач (см. ниже), и продолжай основной этап.
4. Используй существующие компоненты, функции и инфраструктуру; дублирующих систем не создавай.
5. Не исследуй повторно то, что уже изучено и решено (журнал задач, `AI_WORK_STATE.md`).
6. Проверяй результат сам; не проси пользователя о проверках, которые можешь выполнить сам.
7. Без отдельного согласования не меняй действующий сайт, рабочие данные и основные ветки.
8. Отдельно согласуй: публикацию, удаление важных файлов, изменения архитектуры, платные решения.
9. После работы — один короткий отчёт (оформление — `docs/claude/otvety.md`).
