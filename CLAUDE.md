# CLAUDE.md

## Правила работы

Отвечай на русском. Работай экономно по токенам: не анализируй весь проект без необходимости, не читай отчёты/логи/старые markdown без нужды, для каждой задачи сначала определяй минимальный набор релевантных файлов. Открывать больше 3 файлов без вопроса можно всегда, если они реально нужны для задачи (языки, SEO, routes, refactor, дизайн, audit и т.п.). Не показывай полный код файлов — только diff/изменённые фрагменты.

Работай профессионально и критично. Если данных недостаточно — скажи об этом или задай короткий уточняющий вопрос, но только если без этого нельзя безопасно выполнить задачу. Не делай вид, что уверен, если это не так.

## Автономный режим по умолчанию

Claude всегда работает автономно, без того чтобы пользователь каждый раз писал «не спрашивай», «сделай до конца», «commit/push разрешён» и т.п. Это действует для всех задач, если пользователь прямо не написал обратное.

Claude сам: определяет минимальный набор файлов, читает их, выбирает безопасный технический вариант, выполняет задачу, исправляет локальные ошибки от своей же правки, запускает проверки (`npx tsc --noEmit`, `npm run build`), проверяет `git status --short`, при необходимости коммитит/пушит в `test`, даёт короткий финальный отчёт. Без вопросов можно: read-only анализ, `rg`/поиск, проверку импортов и использования файлов, любые read-only git-команды, `node -e` для анализа, dev-routes, локальный refactor в рамках задачи (перенос JSX в общий template, текстов в i18n/data, синхронизацию языковой версии с PL).

Если пользователь пишет «исправь/сделай/поменяй/подготовь/отрефакторь/синхронизируй/добавь/убери» — это прямой мандат на кодовые изменения без дополнительного подтверждения.

Если есть несколько безопасных вариантов, выбирай тот, который: 1) меньше меняет проект; 2) лучше сохраняет текущий дизайн; 3) лучше поддерживает общий skeleton; 4) не меняет SEO-смысл; 5) не ломает PL как source of truth; 6) проще расширяется на будущие языки; 7) не затрагивает цены/контакты/формы/юридический смысл/`master`. Не спрашивай «какой вариант выбрать», если один вариант явно соответствует этим правилам.

Если сомнение не критичное — выбирай минимальный безопасный вариант и продолжай. Если действие рискованное, но можно сначала сделать read-only проверку — сделай её вместо вопроса. Если после проверки риск подтвердился — останавливайся и коротко объясни причину.

### Когда нужно остановиться и спросить

Только в критичных случаях: текущая ветка не `test`; есть неожиданные незакоммиченные изменения; нужно трогать `master`; нужно читать/менять `.env*`; нужно установить/удалить/обновить npm-пакеты; нужно изменить цены, контакты, юридический смысл текста, отправку формы или backend API; нужно изменить URL/slug/canonical/hreflang/sitemap/robots.txt (если это не было явной частью задачи); нужно удалить существующий видимый блок сайта или файл, использование которого не проверено через imports/`rg`/git; build/typecheck не проходит по причине, явно не связанной с текущей правкой; исправление требует большого refactor за пределами задачи; изменение выходит за рамки задания.

Если файл/блок выглядит подозрительным, но нет доказательства риска — сначала проверь imports/`rg`/git-tracking/usage, и только если риск подтвердился — спрашивай.

## Git: commit, push, ветки

Если Claude изменил файлы и задача не запрещает commit/push — можно самостоятельно закоммитить и запушить в `test`, когда: текущая ветка `test`; `git status --short` показывает только ожидаемые файлы задачи; нет изменений в `.env*` или в `master`; не менялись цены/контакты/форма/юридический текст без прямого задания; `npx tsc --noEmit` и `npm run build` прошли. Commit message — короткий, по смыслу, Claude выбирает сам. Push — только `git push origin test`, пуш в `master` запрещён.

`git add -A` — только после проверки `git status --short`, что там только ожидаемые файлы; иначе точечный `git add <path>`.

Перед изменениями молча проверь текущую ветку. Если не `test` — останови работу и ничего не меняй, спроси пользователя (не переключай ветку самостоятельно). Если `test` — продолжай автономно, не спрашивай про ветку каждый раз.

Если пользователь написал «не commit», «не push», «только аудит», «ничего не менять», «read-only» — обязательно соблюдай это ограничение.

## Read-only audit mode

Применяется для задач вида: audit, поиск мусора/неиспользуемых файлов, inspection, read-only анализ структуры без изменений.

Разрешено без вопроса: все read-only git-команды, `ls`, `find`, `rg`, `du`, `wc`, `head`, `tail`, `node -e`, чтение файлов проекта и проверка импортов/ссылок/путей/ассетов — сколько нужно для audit-задачи, без промежуточных подтверждений, до итогового отчёта.

Спрашивай подтверждение только для: удаления файла/папки, изменения файла, commit/push, установки пакета, `git reset/rebase/clean`, любой команды, меняющей проект, чтения `.env*`, изменения кода/SEO/URL/canonical/hreflang/цен/контактов/формы.

Важно: ничего не удаляй и не меняй без отдельного подтверждения в этом режиме; не предлагай удалять `node_modules`, `.next`, `public/images` (без доказательства неиспользуемости конкретного файла), `CLAUDE.md` или файлы правил Claude; никогда не читай `.env*`.

## Безопасность

* Не читай `.env`, `.env.local`, `.env.production`, `.env.development`, ключи, токены, пароли, секреты без разрешения — даже в audit-режиме. Не выводи секреты в ответ.
* Не устанавливай пакеты без подтверждения.
* Не запускай опасные команды: удаление файлов, очистка базы, `git reset/rebase/clean`, деплой, push в `master`, отправка секретов наружу.
* `master` нельзя трогать вообще, ни при каких обстоятельствах. Работай только в `test`, если задание не указывает иное.

## Финальный отчёт

По умолчанию — короткий и практический: что изменено, какие файлы, какие проверки прошли, какой commit/push сделан, что осталось отдельной задачей. Не заканчивай ответ вопросом, если работа выполнена успешно.

Для задач про UI/дизайн/поведение сайта (когда внешний вид/логика должны были остаться как есть, а менялась только скорость/структура под капотом) — вместо списка файлов пиши 1-2 строки по-человечески: что сделано и что визуально/функционально всё так же, как было (например: «Ускорил загрузку меню, всё проверено — сайт выглядит и работает как раньше»). Списки файлов и технические детали — только если пользователь сам спросит подробнее.

Перед такими задачами сам определи (не озвучивая), что должно остаться неизменным, а что — цель правки; не трогай страницы/блоки, не относящиеся к задаче. После завершения — сам проверь результат (headless Chrome, визуальное сравнение до/после на затронутых и на соседних страницах, если код общий). Если задача на деле требует более широких изменений или есть визуальное расхождение, которое нельзя тихо исправить в той же логике — остановись и спроси.

## Изменение сайта

Не давай длинный план перед каждой правкой (короткий план — только если задача неоднозначная/рискованная/затрагивает критичные области). Меняй минимальное количество файлов, без рефакторинга «заодно». Не меняй цены, контакты, юридический смысл текста, отправку формы без подтверждения. Тексты и SEO можно менять, если задача явно про это. Дизайн-правки — только нужный UI-блок, без изменения архитектуры без необходимости. Архитектурный refactor — можно менять общие шаблоны и связанные route/data-файлы, если это прямо относится к задаче.

Специализированная логика по дизайну/языкам/SEO — в path-scoped `.claude/rules/design-guardrails.md` и `.claude/rules/i18n-seo-guardrails.md` (подгружаются автоматически при работе с соответствующими файлами) и в субагентах `ui-design`, `pages`, `seo-content`. Многоязычность: PL — source of truth, Claude синхронизирует версии, а не переводит по строкам; общий шаблон проверяется минимум на PL и UK; будущие RU/EN — через общие шаблоны и i18n/data, не копированием JSX. Архивный подробный справочник (на случай, если в rules/agents не хватило деталей): `claude-instrukcii/claude-dizain.md`, `claude-instrukcii/claude-mnogoyazychnyi-sait-i-seo.md` — открывать вручную по необходимости, не грузится автоматически.

## Отчёты и служебные файлы не хранить в репозитории

Claude никогда не создаёт в проекте файлы только чтобы показать результат работы (`REPORT.md`, `AUDIT.md`, `*-AUDIT.md`, `ANALIZA-*.md`, `PERFORMANCE-REPORT.md`, Lighthouse/QA/screenshot-отчёты, временные `.txt/.json/.html` с результатами проверок и т.п.). Все результаты анализа/аудита/Lighthouse/QA/performance/SEO/security/сравнений — прямо в ответе (в чате), а если слишком объёмно — через Claude Artifact. Файл в проекте ради этого не создаётся.

Исключение — только если пользователь прямо попросил «создай файл ... в проекте».

Также: не коммитить служебные отчёты; временные файлы тестов и Lighthouse/trace/debug — удалять после использования; одноразовые dev-инструменты/зависимости — удалять, если не нужны проекту постоянно. В репозитории — только реальные файлы сайта, разработки, конфигурации и явно запрошенная документация.

## Сохранение решений (для маленьких задач без субагента)

Когда Claude сам (без вызова специализированного субагента) выполняет небольшую задачу и приходит к важному для будущего решению — сохраняет его сразу и дёшево, в рамках текущей работы, без отдельного анализа сессии, без отдельного memory-агента, без пересчитывания истории.

**Решение считается принятым**, без специальных слов вроде «утверждаю»/«финальный вариант»/«запомни», если одновременно: 1) правка реально реализована в коде; 2) пользователь не попросил её откатить/поправить после того как увидел результат; 3) пользователь перешёл к следующей теме/задаче. Пример: иконка была 42px, потом 40px, пользователь переключился на другую тему — принятое состояние 40px, сохранять всю историю (42→40) не нужно, только финальный факт.

НЕ считается принятым: то, что Claude только предложил, но не реализовал; временные/диагностические/тестовые правки; то, что ещё обсуждается; вариант, сразу за которым последовала правка; правка ради проверки гипотезы; то, что не повлияет на будущую работу.

Сохранять только то, что реально поможет не переобсуждать то же самое, не откатиться случайно к старому варианту, сохранить визуальную/техническую преемственность проекта между сессиями (выбранные размеры/пропорции, финальный внешний вид, важные цвета, поведение интерфейса, устойчивые предпочтения пользователя, значимые технические решения, проверенные решения сложных проблем). Если пользователь позже меняет решение — не добавляй новую запись поверх старой, обнови существующую запись на месте (пример: «Мобильный футер: иконки 40px» → пользователь меняет на 44px и идёт дальше → запись становится «...иконки 44px», без истории старого значения, если оно не имеет отдельной ценности).

Сохраняй в максимально узкую подходящую память: UI/UX → `ui-design`; конкретная страница → `pages`; SEO/контент/локализация → `seo-content`; производительность → `performance`; архитектура/build/dev → `tech`. Корневая память (Auto Memory) — только для знания, реально полезного вне одной специализации; не дублируй один факт в нескольких местах. Лучше не сохранить мелкую деталь, чем засорить память тысячами незначительных записей — критерий: «действительно ли это знание пригодится Claude в будущей работе над проектом».

## Локальный dev-сервер

Проект должен быть доступен на `http://localhost:3000` во время и после задач.

Используй `npm run dev:turbo` (не `npm run start`, если явно не нужна проверка production-сборки). Не останавливай уже работающий сервер без необходимости; если пришлось остановить/перезапустить — обязательно запусти снова перед завершением задачи. Не оставляй несколько dev-серверов одновременно; не открывай отдельное внешнее окно терминала. Перед завершением проверь, что `http://localhost:3000` реально отвечает.

## Команды и Antigravity/IDE-подтверждения

Запускай команды напрямую из текущей директории (workspace уже открыт в корне) — не добавляй `cd C:\...`, если терминал уже там. Предпочитай простые отдельные команды из allow-list (`npm run build`, `npx tsc --noEmit`, `git status --short`, `git diff --stat`, `git branch --show-current`, `rg`, `find`, `ls`, `node -e`) вместо длинных compound-команд с pipes/`;`/`cd`/`Select-Object -Last` — это снижает число системных подтверждений Antigravity/IDE. Если IDE всё равно запрашивает подтверждение безопасной команды — это не вопрос Claude к пользователю; после разрешения среды продолжай выполнение, не меняя план.

Не используй `/lint` как skill — сначала проверь `package.json` на реальный npm-script и запускай его напрямую, если он есть.

Для очень длинных многосессионных задач — веди `OPTIMIZATION_PROGRESS.md` с текущим этапом/сделанным/остатком/метриками/командой для продолжения после лимита.

## Compact Instructions

При сжатии контекста сохраняй: утверждённые пользователем решения; текущую цель; что сделано и что осталось; изменённые файлы; важные технические причины решений; постоянные правила проекта (этот файл, `.claude/rules/`, `.claude/agents/`); явные запреты/требования пользователя; выбранные варианты дизайна/UX; состояние, нужное для безопасного продолжения (ветка, dev-сервер, незакоммиченное).

Не сохраняй подробно: отвергнутые варианты, длинные промежуточные рассуждения, повторяющиеся сообщения, большие логи уже решённых проблем, отменённые эксперименты.

## Специализированные субагенты

В `.claude/agents/` — 5 субагентов: `ui-design`, `pages`, `seo-content`, `performance`, `tech`, у каждого своя память (`memory: local`). Claude сам определяет область задачи и делегирует подходящему субагенту, когда это реально экономит основной контекст; не вызывает несколько субагентов без необходимости и не грузит чужую память «на всякий случай». Простые мелкие задачи, где субагент обошёлся бы дороже своей пользы, Claude делает сам напрямую (см. «Сохранение решений» выше). Цель — экономия токенов, а не число вызовов агентов.
