## Автономный режим по умолчанию

Работай автономно в рамках задачи и ограничений пользователя; разрешение менять код не разрешает commit, push или merge.

Claude сам: определяет минимальный набор файлов, читает их, выбирает безопасный технический вариант, выполняет задачу, исправляет локальные ошибки от своей же правки, запускает проверки (`npx tsc --noEmit`, сборка — в копии), проверяет `git status --short`, даёт финальный отчёт. Без вопросов можно: read-only анализ, `rg`/поиск, проверку импортов и использования файлов, любые read-only git-команды, `node -e` для анализа, dev-routes, локальный refactor в рамках задачи (перенос JSX в общий template, текстов в i18n/data, синхронизацию языковой версии с PL).

Если пользователь пишет «исправь/сделай/поменяй/подготовь/отрефакторь/синхронизируй/добавь/убери» — это прямой мандат на кодовые изменения без дополнительного подтверждения, если задача понятна и не попадает в случаи из «Когда нужно остановиться и спросить».

Если есть несколько безопасных вариантов, выбирай тот, который: 1) меньше меняет проект; 2) лучше сохраняет текущий дизайн; 3) лучше поддерживает общий skeleton; 4) не меняет SEO-смысл; 5) не ломает PL как source of truth; 6) проще расширяется на будущие языки; 7) не затрагивает цены/контакты/формы/юридический смысл/`master`. Не спрашивай «какой вариант выбрать», если один вариант явно соответствует этим правилам.

Задача понятна — мелкие технические решения принимай сам и не отвлекай вопросами: при некритичном сомнении выбирай минимальный безопасный вариант и продолжай. Задача неоднозначна, решение существенно влияет на результат или может нарушить существующие настройки — сначала спроси. Если действие рискованное, но можно сначала сделать read-only проверку — сделай её вместо вопроса; если риск подтвердился — останавливайся и коротко объясни причину. Ограничения безопасности и согласования (ниже, «Git», «Безопасность») действуют всегда.

### Когда нужно остановиться и спросить

Кроме неоднозначных задач (см. выше), обязательно — в этих случаях: текущая ветка не подходит для задачи (см. «Ветки» ниже); есть неожиданные незакоммиченные изменения; нужно трогать `master`; нужно читать/менять `.env*`; нужно установить новые, удалить или обновить npm-пакеты (восстановление по package-lock — `npm install` без новых пакетов — разрешено пользователем 2026-10-24, без вопроса); нужно изменить цены, контакты, юридический смысл текста, отправку формы или backend API; нужно изменить URL/slug/canonical/hreflang/sitemap/robots.txt (если это не было явной частью задачи); нужно удалить существующий видимый блок сайта или файл, использование которого не проверено через imports/`rg`/git; build/typecheck не проходит по причине, явно не связанной с текущей правкой; исправление требует большого refactor за пределами задачи; изменение выходит за рамки задания.

Если файл/блок выглядит подозрительным, но нет доказательства риска — сначала проверь imports/`rg`/git-tracking/usage, и только если риск подтвердился — спрашивай.

## Git: commit, push, ветки

Commit, push и merge — только после явного разрешения пользователя на соответствующее действие. Перед разрешёнными Git-изменениями: ветка соответствует задаче (см. «Ветки»); для `master` пользователь отдельно назвал конкретное действие; `git status --short` содержит только ожидаемые файлы задачи; нет изменений `.env*`; цены/контакты/форма/юридический текст менялись только по прямому заданию; если менялся код сайта — `npx tsc --noEmit` прошёл и сборка прошла (в копии, см. `.claude/rules/optimization-check.md` §5); для правок только инструкций и документов сборка не нужна. Commit message — короткий, по смыслу. Push выполняй только в явно названную пользователем ветку, каждый раз по отдельному разрешению.

`git add -A` — только после проверки `git status --short`, что там только ожидаемые файлы; иначе точечный `git add <path>`.

**Ветки:**
* `test` — правки, оптимизация и проверки существующего сайта.
* Новая страница — в отдельной ветке `pages/<название-страницы>` (можно в отдельной рабочей копии со своим портом). Создание ветки и включение страницы в `test`, меню или на главную — только по согласованию с пользователем.
* Любая другая ветка — только если пользователь явно назвал её для этой задачи.
* `master` — защищена, см. «Безопасность».

Перед изменениями молча проверь текущую ветку. Если она соответствует задаче по правилам выше — продолжай автономно, не спрашивай про ветку каждый раз. Если не соответствует — останови работу и ничего не меняй, спроси пользователя (не переключай ветку самостоятельно).

Если пользователь написал «не commit», «не push», «только аудит», «ничего не менять», «read-only» — обязательно соблюдай это ограничение.

## Read-only audit mode

Применяется для задач вида: audit, поиск мусора/неиспользуемых файлов, inspection, read-only анализ структуры без изменений.

Разрешено без вопроса: все read-only git-команды, `ls`, `find`, `rg`, `du`, `wc`, `head`, `tail`, `node -e`, чтение файлов проекта и проверка импортов/ссылок/путей/ассетов — сколько нужно для audit-задачи, без промежуточных подтверждений, до итогового отчёта.

Спрашивай подтверждение только для: удаления файла/папки, изменения файла, commit/push, установки пакета, `git reset/rebase/clean`, любой команды, меняющей проект, чтения `.env*`, изменения кода/SEO/URL/canonical/hreflang/цен/контактов/формы.

Важно: ничего не удаляй и не меняй без отдельного подтверждения в этом режиме; не предлагай удалять `node_modules`, `.next`, `public/images` (без доказательства неиспользуемости конкретного файла), `CLAUDE.md` или файлы правил Claude; не читай `.env*` без разрешения (см. «Безопасность»).

## Безопасность

* Не читай `.env`, `.env.local`, `.env.production`, `.env.development`, ключи, токены, пароли, секреты без разрешения — даже в audit-режиме. Не выводи секреты в ответ.
* Не устанавливай новые пакеты без подтверждения. Исключение: `npm install` для восстановления библиотек по package-lock (без новых пакетов и без изменения package.json) — разрешён постоянно.
* Не запускай опасные команды: удаление файлов, очистка базы, `git reset/rebase/clean`, деплой и отправка секретов наружу.
* Ветка `master` защищена. Любые изменения, commit, push и merge разрешены только после моего явного согласия на конкретное действие. Общее разрешение работать над проектом не считается разрешением изменять `master`. Работай в ветке, подходящей для задачи (см. «Ветки»).

В пределах лимита ответа, по-человечески: результат, проверки, выполненные Git-действия, остаток работы. Список файлов и технические детали — только если пользователь спросит или задача сама техническая. Не заканчивай вопросом, если задача выполнена.

Списки файлов и технические детали — только если пользователь сам спросит подробнее.

Перед такими задачами сам определи (не озвучивая), что должно остаться неизменным, а что — цель правки; не трогай страницы/блоки, не относящиеся к задаче. После завершения — финальная визуальная проверка по правилу «Визуальная проверка» выше. Если задача на деле требует более широких изменений или есть визуальное расхождение, которое нельзя тихо исправить в той же логике — остановись и спроси.

## Разработка Omobonus Workspace (утверждено пользователем 2026-10-24)

Для всех этапов разработки Workspace (код — `omobonus-workspace/app`, облачная панель — `omobonus-panel`) действует этот подход; он важнее общих правил о согласованиях выше. Цель — быстро получать готовые работающие функции. Приоритет: готовые функции, минимальная сложность, сохранность данных.

1. Получив задачу, сам выполняй весь согласованный этап: исследование, реализацию, тестирование, исправление ошибок.
2. Не спрашивай разрешения на мелочи. Безопасные изменения кода и commit + push в рабочие ветки (не `main`/`master`) разрешены.
3. Незначительные замечания, которые не мешают работе, — в журнал задач (см. ниже), и продолжай основной этап.
4. Используй существующие компоненты, функции и инфраструктуру; дублирующих систем не создавай.
5. Не исследуй повторно то, что уже изучено и решено (журнал задач, `AI_WORK_STATE.md`).
6. Проверяй результат сам; не проси пользователя о проверках, которые можешь выполнить сам.
7. Без отдельного согласования не меняй действующий сайт, рабочие данные и основные ветки.
8. Отдельно согласуй: публикацию, удаление важных файлов, изменения архитектуры, платные решения.
9. После работы — один короткий отчёт одним блоком для копирования (см. «Финальный отчёт»).

## Сохранение состояния и решений

В начале сессии читай в `AI_WORK_STATE.md` только краткую шапку (до маркера «КОНЕЦ ШАПКИ»); старые этапы — только при необходимости, через поиск по «ЭТАП N» или hash. После важного этапа и перед завершением добавляй короткую запись этапа в раздел «ЖУРНАЛ ЭТАПОВ» (новые сверху) и обновляй шапку: задача, сделанное, остаток, Git-состояние (hash коммитов) и следующий шаг. Историю не удалять, hash коммитов, результаты и решения не терять. Журнал отслеживается Git: после завершения этапа он должен быть обновлён и сохранён в коммите (вместе с этапом, по общему правилу разрешения на commit); явный запрет на запись имеет приоритет. Отдельный служебный коммит только ради записи хеша предыдущего коммита не делать: дата, название этапа и статус достаточны, хеш дописывается при следующем плановом изменении журнала. Важные решения сохраняй сразу, без отдельного анализа сессии или memory-агента.

**Решение считается принятым**, без специальных слов вроде «утверждаю»/«финальный вариант»/«запомни», если одновременно: 1) правка реально реализована в коде; 2) пользователь не попросил её откатить/поправить после того как увидел результат; 3) пользователь перешёл к следующей теме/задаче. Пример: иконка была 42px, потом 40px, пользователь переключился на другую тему — принятое состояние 40px, сохранять всю историю (42→40) не нужно, только финальный факт.

НЕ считается принятым: то, что Claude только предложил, но не реализовал; временные/диагностические/тестовые правки; то, что ещё обсуждается; вариант, сразу за которым последовала правка; правка ради проверки гипотезы; то, что не повлияет на будущую работу.

Сохранять только то, что реально поможет не переобсуждать то же самое, не откатиться случайно к старому варианту, сохранить визуальную/техническую преемственность проекта между сессиями (выбранные размеры/пропорции, финальный внешний вид, важные цвета, поведение интерфейса, устойчивые предпочтения пользователя, значимые технические решения, проверенные решения сложных проблем). Если пользователь позже меняет решение — не добавляй новую запись поверх старой, обнови существующую запись на месте (пример: «Мобильный футер: иконки 40px» → пользователь меняет на 44px и идёт дальше → запись становится «...иконки 44px», без истории старого значения, если оно не имеет отдельной ценности).

Сохраняй в максимально узкую подходящую память: UI/UX → `ui-design`; конкретная страница → `pages`; SEO/контент/локализация → `seo-content`; производительность → `performance`; архитектура/build/dev → `tech`. Корневая память (Auto Memory) — только для знания, реально полезного вне одной специализации; не дублируй один факт в нескольких местах. Лучше не сохранить мелкую деталь, чем засорить память тысячами незначительных записей — критерий: «действительно ли это знание пригодится Claude в будущей работе над проектом».

Проект должен быть доступен на `http://localhost:3000` во время и после задач.

Не оставляй несколько dev-серверов одновременно; не открывай отдельное внешнее окно терминала. Перед завершением проверь, что `http://localhost:3000` реально отвечает.

## Команды и Antigravity/IDE-подтверждения

Запускай команды напрямую из текущей директории (workspace уже открыт в корне) — не добавляй `cd C:\...`, если терминал уже там. Предпочитай простые отдельные команды из allow-list (`npx tsc --noEmit`, `git status --short`, `git diff --stat`, `git branch --show-current`, `rg`, `find`, `ls`, `node -e`) вместо длинных compound-команд с pipes/`;`/`cd`/`Select-Object -Last` — это снижает число системных подтверждений Antigravity/IDE. Если IDE всё равно запрашивает подтверждение безопасной команды — это не вопрос Claude к пользователю; после разрешения среды продолжай выполнение, не меняя план. Сборку (`npm run build`) запускай только в отдельной копии проекта (см. «Git»), чтобы не нарушить работающий сайт на localhost:3000.

Не используй `/lint` как skill — сначала проверь `package.json` на реальный npm-script и запускай его напрямую, если он есть.
