Задача неоднозначна, решение существенно влияет на результат или может нарушить существующие настройки — сначала спроси. - Отчёты и результаты проверок в проекте не создавать: резюме — в ответе, полный отчёт — отдельным файлом вне проекта.
- В начале работы читай в `AI_WORK_STATE.md` только краткую шапку (до «КОНЕЦ ШАПКИ»); после этапа обновляй результат и следующий шаг.

- Контекст переполнен — обнови состояние, предложи новую сессию.

## Цены/сроки услуг и синхронность 3 языков (pl/ru/uk) — обязательно к прочтению перед правкой цен/сроков или текстов в `services-data*.ts`

### Архитектура: единый источник чисел для 3 языков

Цены и сроки всех 13 услуг (510 позиций) рендерятся НЕ напрямую из `item.price`/`item.duration` в языковых файлах, а через общую схему:

- `src/lib/services-pricing-data.ts` — `migratedPrice`/`migratedDuration`: по каждой id-позиции (`slug::section[.subcategory].index`) хранит `{ wrapperKey, numbers: string[] }`. **Здесь и только здесь меняются сами числа** — одна правка сразу отражается на всех 3 языках.
- `src/lib/services-pricing-wrappers.ts` — `PRICE_WRAPPERS`/`DURATION_WRAPPERS`: словарь текста вокруг чисел ("od", "+ część/деталь/частина", "GRATIS" и т.п.) на pl/ru/uk, с плейсхолдерами `{0}`, `{1}`...
- `src/lib/services-pricing.ts` — `getDisplayPrice(slug, path, locale, fallback)` / `getDisplayDuration(...)`: собирает итоговую строку из числа + перевода обёртки. Рендерящие компоненты (`service-accordion.tsx`) вызывают только эти функции; `item.price`/`item.duration` в `services-data.ts`/`-ru.ts`/`-uk.ts` используются исключительно как `fallback`-текст (для положений вне общей схемы — таких сейчас 0 из 510) и как документация "что должно отображаться".

**Правило:** число цены/срока нельзя хардкодить отдельно в PL/RU/UK языковых файлах. Если нужно поменять число — меняй `services-pricing-data.ts` (все 3 языка получат правку разом), и при этом также обнови `item.price`/`item.duration` (raw fallback-текст) во всех 3 языковых файлах, чтобы он не разошёлся с тем, что реально выводит `getDisplayPrice`/`getDisplayDuration` (это проверяется `check:i18n-sync`, см. ниже). Если нужен новый формат обёртки — добавь запись в `PRICE_WRAPPERS`/`DURATION_WRAPPERS` (даже одноразовую) вместо точечного текста в языковом файле.

### Правило синхронного перевода (важно: RU/UK — не отдельная система)

RU и UK версии сайта изначально созданы одноразовым ИИ-переводом польского оригинала (весь текст переведён и вставлен за один заход), а не отдельной автоматической системой перевода на сайте. Из этого следует:

**Любая правка текста/структуры в одном языковом файле должна быть синхронно переведена на остальные 2 языка в ТОМ ЖЕ ПРОХОДЕ, тем же ИИ, который вносит правку** — не откладывать "на потом", не полагаться на отдельный процесс/скрипт перевода (такого на сайте нет и не планируется). Если меняешь PL-текст услуги/секции/подкатегории — в этом же ответе внеси соответствующий перевод в `services-data-ru.ts` и `services-data-uk.ts`. PL остаётся source of truth (см. `.claude/rules/i18n-seo-guardrails.md`), но перевод не может "зависнуть неготовым" до следующей сессии.

### Структурные изменения — проверяй id-соответствие

Если меняешь состав секций/подкатегорий/позиций (добавил, удалил, переставил) — id (`section.id`, `subcategory.id`) и порядок позиций должны совпадать 1:1 между `services-data.ts`, `services-data-ru.ts`, `services-data-uk.ts`. Позиционный id (`slug::section[.subcategory].index`) вычисляется по индексу в массиве — рассинхронизация порядка/количества элементов молча ломает связку "число ↔ позиция" для всех 3 языков сразу.

### Обязательный чеклист перед коммитом

Коммит, затрагивающий `services-data.ts`, `services-data-ru.ts`, `services-data-uk.ts`, `services-pricing-data.ts` или `services-pricing-wrappers.ts`, требует ПЕРЕД коммитом:

```
npm run check:i18n-sync
```

Скрипт (`scripts/check-i18n-sync.ts`) сверяет: (1) список услуг/секций/подкатегорий и число позиций 1:1 между pl/ru/uk; (2) числовое ядро `priceTiers`/`subcategory.price` (wynajem-drukarek, drukarka-zastepcza) между pl/ru/uk; (3) что `item.price`/`item.duration` в языковых файлах не разошлись с тем, что реально строит `getDisplayPrice`/`getDisplayDuration` через общую схему. Exit code 0 + "OK" — можно коммитить; ненулевой exit code и список расхождений (с id и файлом) — сначала исправь.

Скрипт проверен на 5 типов поломок (испорченный id, пропущенная позиция, лишняя позиция, число в общем файле без обновления языковых файлов, пустая строка) — во всех случаях ловит и указывает конкретный id+файл.

### Частые ошибки при работе с этой системой (реальные инциденты, не гипотезы)

1. **Сравнение по польскому тексту вместо позиции.** В `service-accordion.tsx` (таблица wynajem-drukarek) логика ветвления строк была написана как `row.label === 'Czynsz wynajmu (zł miesięcznie)'` — сравнение с польским текстом, которое истинно только на `pl`; на RU/UK молча падало в fallback без правильного форматирования. Правило: для веток, зависящих от **какая это строка/позиция** (а не от языка), сравнивай по `rowIdx`/index/id, никогда по конкретному тексту на одном языке. Если нужно распознать структуру текста (например «хвостовая скобка» `(...)`/`[...]`), пиши языконезависимый regex по структуре, а не по конкретным словам (`mono`/`kolor`).

2. **Забытый дубль-секция при переводе.** В `serwis-drukarek-laserowych` (RU/UK) при одноразовом переводе PL остался лишний объект-дубликат `naprawy-tasma`, который PL явно отфильтровывает кодом (`applyLaserElectronicsSubcategory`, `sub.id !== 'naprawy-tasma'`) — перевод скопировал структуру ДО фильтрации. Из-за этого в RU/UK было на 1 пункт больше, а «настоящая» подкатегория — на 1 пункт меньше, чем в PL. Правило: при переводе/синхронизации подкатегорий проверяй не только исходные данные, а и то, что реально проходит через build-time фильтры/трансформации PL — id и count должны совпадать после всех преобразований, не до них.

3. **Скрытый дубль-источник данных.** `WynajemTable.tsx` — старый компонент со своим отдельным хардкод-источником чисел (`plan1/plan2/plan3`), не проходящий через общую схему `getDisplayPrice`/`getDisplayDuration`. Он не мёртвый (импортируется, условно достижим при `subcategory.items.length === 0` и отсутствии `priceTiers`/`price`), но сейчас не рендерится ни при каких реальных данных. Риск: если в будущем кто-то уберёт `priceTiers` у подкатегории wynajem-drukarek, сайт молча переключится на этот старый источник с своими цифрами. Правило: перед тем как полагаться на «этот компонент не используется», проверяй достижимость по реальным данным (написать временный скрипт-обходчик), а не только по статическому чтению кода.

4. **Мёртвый код/устаревшие комментарии после миграции.** После завершения унификации в `services-pricing.ts` остался неиспользуемый экспорт `canonicalPricing` (диагностика этапа 1, только для уже удалённого temp-скрипта) и комментарий, утверждавший «19 цен и 3 срока не мигрированы» — хотя по факту стало 510/510. Правило: когда переходишь от промежуточного этапа к финальному — проверяй `rg` не только на «работает ли», но и на «остались ли ссылки/актуальны ли комментарии», иначе следующий ИИ поверит устаревшему комментарию вместо кода.

### Правила ответов пользователю

- Писать кратко, понятно и по-человечески.
- Проблему объяснять простыми словами: что произошло, почему и что нужно сделать.
- Формулировать ответы так, чтобы их можно было переслать в другой чат без дополнительного редактирования.
- Всё, что пользователь должен скопировать (команды, тексты для замены и другие готовые материалы), давать отдельным кодовым блоком с кнопкой копирования. Исключение: ссылки всегда оформлять кликабельными Markdown-ссылками вне кодовых блоков.
- Все ссылки давать кликабельными Markdown-ссылками, а не обычным текстом. Не помещать ссылки в кодовый блок.
- Не показывать промежуточную работу в переписке; показывать только итоговый ответ после завершения задачи.
- Перед сдачей любой задачи обязательно самостоятельно проверить результат в браузере: внешний вид, функциональность, консоль, Network и мобильную версию. При ошибках исправлять их и повторять проверку. Не сообщать «готово», пока результат не проверен фактически.
- Перед ответом передавать только фактически проверенные решения и проверенные команды. Не писать предположения или непроверенные варианты. Сначала выполнить все доступные безопасные проверки и действия, затем дать итоговый ответ с отдельными блоками команд для копирования.
